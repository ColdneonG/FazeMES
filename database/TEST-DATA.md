# FazeMES 完整测试数据集

本数据集用于当前 Windows 本地开发环境的功能验收、演示和回归。所有企业、人员、地址、材料价格、检验读数、工时及异常均为虚构测试数据。业务日期使用上海时区，以生成当天为基准。

## 1. 初始化与复核

当前本机环境可直接双击仓库根目录的 `重置业务数据并保留配置.cmd`。它会自动准备数据库和缓存服务，备份并重建完整测试数据，启动全部项目服务并打开 `http://127.0.0.1:5173`。无需手动启动 MySQL、Redis 或另外打开终端。每次执行都会重建业务数据，本地管理员人脸及业务助手、JEV 配置保留。

窗口会显示四个步骤，结束后保留成功或失败信息。日志位于 `.runtime/logs/reset-and-start-*.log`。入口会自动查找 PowerShell 7，并支持本机已有的安装路径回退；不会修改系统执行策略或系统环境变量。首次使用所需的 Java、Node、Python、MySQL 和前端依赖仍须按项目环境要求安装。

命令行也可执行 `pwsh -NoProfile -File deploy/reinitialize-and-start.ps1 -CheckOnly` 只检查环境；添加 `-NoBrowser` 可在完整执行后保持浏览器关闭，添加 `-Build` 可在重建前重新编译后端。

在仓库根目录执行：

```powershell
python -m pip install -r deploy/requirements.txt
pwsh -NoProfile -File deploy/reset-test-data.ps1
```

该命令会替换本机 `127.0.0.1:3308/yudao_mes` 的全部 MES 数据、旧测试账号及业务日志。它会验证实际 MySQL 数据目录属于本项目，停止本项目后端，完整备份数据库，再重建数据、刷新专用 Redis DB0、启动后端，最后执行真实业务接口和一致性校验。

保留数据库结构、迁移记录、管理员原密码、菜单、字典及本地运行配置。上述不带 -KeepManualConfig 的底层命令与双击入口不同：旧的客户门户账号、人脸特征、AI 模型密钥、外部模型用量及历史会话随 MES 数据清除。系统管理员仍从 `.runtime/secrets.local.json` 读取原有凭据。

完整数据库备份和 SHA-256 校验信息位于 `.runtime/backups/`。首次原库备份保持原文件永久保留，并由 `testdata-original-backup.json` 固定登记；已有环境首次应用该策略时，会核验并登记最早的自动备份。后续自动备份使用 `testdata-before-*.sql.gz`，同名 `.json` 同时记录压缩文件和解压后 SQL 的大小及 SHA-256；脚本完整读回校验压缩数据后才删除对应的未压缩副本。备份包含敏感运行数据，已由仓库忽略规则排除，不应提交。

成功后仅保留首次原库备份和最近 **3 份**后续自动备份。双击入口会等待数据验收及全部服务启动成功，再整理备份；直接执行 `deploy/reset-test-data.ps1` 则在数据库验收成功后整理。重建、校验或服务启动失败时不清理旧备份；连续失败期间可能临时超过 3 份，以保留恢复所需数据。下一次完整成功后自动恢复保留数量。现存旧格式的自动备份也会在成功整理时迁移为压缩格式；手工快照、其他功能的历史备份、JAR 文件、无校验登记的 SQL 和未完成的备份文件不在清理范围内。

恢复压缩备份时，先使用支持 gzip 的工具解压为 `.sql`，再按本机数据库恢复流程导入；可用同名 `.json` 中的 `sqlSha256` 校验解压结果。首次原库备份仍可直接按 `.sql` 使用。

只复核当前测试基线：

```powershell
pwsh -NoProfile -File deploy/reset-test-data.ps1 -VerifyOnly
```

结果保存在 `.runtime/testdata-verification.json`；编码及单据 ID 登记保存在 `.runtime/testdata-state.json`。校验包含固定场景的数量与状态断言。手工继续处理待办后，一部分场景状态发生变化属于正常情况；重新验收固定基线时应重新生成数据。

接口阶段失败时，修复原因后可执行：

```powershell
python -X utf8 database/tools/reset_test_data.py api
```

接口检查点只重放同一轮已成功写入检查点的调用结果，从中断位置继续，避免重复采购、扣料、入库或销售。若进程恰在数据库提交与本地检查点写入之间中断，可能需要核对已生成单据后完整重建；检查点不承诺跨进程崩溃的严格一次执行。检查点属于同一生成日期和请求序列；修改此前请求参数时必须完整重建。检查点不保存管理员登录令牌。未完成业务接口阶段的数据不能标记为验收通过。

## 2. 数据设计规则

### 生产大屏增量演练

已有完整测试库需要补充近期大屏场景时，先正常启动项目，再执行：

```powershell
python -X utf8 database/tools/testdata_dashboard.py
python -X utf8 database/tools/testdata_dashboard.py --verify-only
```

第一条先保存并校验完整备份，再通过正常业务 API 增量生成最近连续七天的演练记录，不清空原有数据。覆盖所有启用车间，每车间有独立演练工位及绑定设备、多城市客户工单、实际领料耗料与部分报工产出，以及当日首检草稿和物料补给安灯。使用 `TST-DASH-` 稳定编码，同一日期重复执行会复用已有单据及完成状态；不要在人工继续处理这些演练单据后将脚本当成业务修复工具。

历史报工业务日期明确标注为合成回填；审批、库存流水及创建时间保留真实执行时间。检验草稿的预填读数不表示已放行，部分报工后的原料及产出保留在对应工单线边。大屏设备图仍是台账状态，不表示已接入现场实时采集。

结果保存在 `.runtime/dashboard-fixtures-verification.json`，增量前备份为 `.runtime/backups/dashboard-before-*.sql`。验收逐一检查全厂、每个启用车间及演练工位的当日任务、产量、七日趋势、设备、工单、地图和异常待办，并检查库存流水与数量守恒。完整重建测试数据时也会生成这组场景。

大屏默认显示当天；日期没有生产数据时会提示查看当前筛选范围最近有数据的日期，不会自动挪动历史单据或将示例地图替换为业务数据。已有工位没有任务时显示“所选日期未排产”；趋势仍显示完整七天坐标。正常停产日可以为零，不需要为填满图表制造业务记录。

| 企业与租户 | 一家虚构测试工厂；所有业务关系同租户。客户隔离由独立门户账户验证。 |

| 数量 | 使用十进制；正数量、零库存、小数数量、整批大数量分开设置；库存不得负数。 |
| 金额 | 人民币、不含税。标准预算、真实测试采购价、实际耗料成本与销售价格分别记录，不用标准价补齐未知实际成本。 |

| 关系 | 主从单据、物料、批次、仓库层级、工单及前序报工完整关联。多态来源另做专项校验。 |
| 已执行数据 | 采购、领料、报工、耗料、产出、成品入库、结算、检验、销售、退货等通过正常接口生成。 |

## 7. 质量场景

IQC、IPQC、OQC、RQC 均有模板、指标快照、来源单据及待处理样本。尺寸、螺纹、扭矩、外观和文本指标分别设置工具、方法、上下限与单位；缺陷按严重等级分类。

已完成 IQC 包含全合格和不合格；销售 OQC 包含放行与失败；客户 RQC 包含全合格、混合拆分和全不良。来源单的物料、客户或供应商、批次、数量、质检标识与检验记录逐项核对。

独立的生产终检产品按直径 10.00±0.10 mm 逐件测量，保留 15 份实测样本。待检 6 件不提前判定质量，另一组 10 件中 2 件超差，合格 8 件正常入库，不良 2 件保留在线边等待处置。当前服务按产出行区分同一生产批次的合格与不良数量，未拆出质量子批；入库受合格数量额度控制，不将该批次描述为全部合格，也不把末序不良强行按损耗结案。

IPQC 的工序检验、首检、巡检、自检、成品检验、末检关联有效的已确认工单及真实工位。草稿里预填的读数仍须质检员审核；草稿不构成检验放行证据。

- 12 台设备，6 类设备，7 项点检/保养项目；生产设备与维修测试台分别设置。
- 45 天历史及当日点检/保养任务，包含待认领、已认领和已完成；完成记录与任务行一一对应。
- 维修覆盖草稿、维修中、待验收、验收通过、验收失败退回；异常检查与自动报修有唯一来源。
- 12 项工装，包含按编码和按数量管理、按日期和次数维护、在库/领用/维修/报废及零可用边界。
- 6 个班组、5 种排班方案、连续 91 天日历；单白班、两班倒和三班倒，包含跨午夜夜班及轮换。
- 相同人员的班次不重叠；测试调休、停工日期明确标为合成排班，不能当成法定节假日。
- 72 条安灯呼叫，覆盖三级严重度、六类原因和未处置/已处置。

## 9. 门户、异常、报表与知识

门户有受理、拒绝、待处理和其他客户的申请；通过真实接口验证重复提交幂等、停用登录拒绝、匿名拒绝和客户隔离。测试门户会话生成后退出，报告不含登录令牌。

生产决策中心包含六类异常及建议转异常，覆盖创建、指派、处理中、待验证、关闭、复发重开和验证失败退回；根因、措施、证据、版本和事件历史完整。四组业务对话包含库存台账分组追问、标准/实际成本、缺料风险和时间澄清；全部使用规则查询，无外部模型调用。

五类业务报表使用内置白名单数据集，包括工单、报工、库存、质检和设备。前两份报表发布 R1，其中第一份继续保留 R2 草稿，其他三份保持草稿；普通查询者仍读取已发布版本。知识库包含 3 个库、6 份合成文档和 18 个分块；UTF-8 文件、SHA-256、字符偏移、片段哈希和下载内容一致。文档草稿不会伪装成模型生成回答。

## 10. 验收及有意保留的空表

验收分为数据库一致性、正向业务链、负向拦截、接口可读性及角色权限：

1. 库存余额等于正负库存流水，库存维度一致且非负；工单线边库存必须有所属工单。
2. 工单数量、任务、报工合格/不良/待检数量守恒；前序来源分配不超可用份额，冻结来源可追溯。
3. 已完工产品数量完整，线边已清理；已结算工单有实际材料、人工和制造费用依据。
4. 采购、销售、退货的头、行、拣货/上架明细和检验来源保持一致；未过账草稿无交易流水。
5. 销售履约与退货来源额度独立校验；隔离品的数量及存放位置可核对。
6. 设备任务、维修、排班、SOP、SN、客户门户和异常事件分别执行专项检查。
7. 动态发现 MES 查询接口，并检查详情、看板、成本、追溯和报表预览；参数不全与服务器错误分别记录，不算通过。
8. 验证仓管成本访问被拒绝、操作员无库存写权限、只读角色无写权限；角色校验不执行试探性业务修改。

部分表可以有意为空：人脸特征需要本人录入；模型配置、模型调用用量与 Jev 结果需要真实外部调用；旧版兼容工艺附件或流转表只有对应业务实际使用时才建立；历史质量核查表仅针对可靠历史异常证据生成，不人为制造脏历史来填表。验收报告逐张列出有数据表及空表，完整性以业务覆盖和证据一致性判断。

生成代码位于 `database/tools/reset_test_data.py` 及 `testdata_*.py`。主数据、待办与历史配套记录按结构校验写入；需要触发业务规则的记录使用正常业务接口。任何生成失败都会保留备份、状态及检查点，不能只凭插入行数声称完成。
