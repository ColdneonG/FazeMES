# Jev 异常分流试点

入口：生产决策中心 → 异常闭环。当前功能为异常分类与实际部门建议，人工确认后创建异常。千问聊天模型配置独立保留。

## 本机启用

1. 获取自己的 TypeSafe API Key：https://console.typesafe.ai/ 。之前导出的阿里云千问密钥不能用于 Jev。
2. 点击“Jev分流配置”，输入 TypeSafe 密钥，保留固定模型版本 `jev-1.13.0`，启用并保存。
3. 点击“测试已保存配置”。此操作请求真实 Jev 接口，使用合成示例，不创建异常或试点反馈记录。
4. 建立异常，填写标题、描述，点击“分析分类与建议部门”。检查建议，点击“将可用建议填入表单”，也可手动调整。最后点击“建立跟进”才会创建异常。

官方接口固定为 `POST https://api.typesafe.ai/v1/systemone`，使用 `state`、`model` 和两个独立 `choice` 问题。API 文档：https://docs.typesafe.ai/api 。本功能没有使用截图中无法确认归属的第三方服务，也不复用阿里云密钥。

仅发送本次标题、问题描述和当前租户启用部门的名称作为候选；不发送附件、用户列表、库存或完整生产数据库。部门最多254项，加上“无法判断”选项满足接口限制。模型没有合适候选时返回待人工分派。

## 结果与记录

- 模型返回后不改变工单、安灯状态、负责人或库存；建议必须人工确认保存。
- 标题或描述改变会清除旧建议，服务端也校验内容哈希。建议24小时过期，只能由生成建议的用户在同一租户确认一次。
- 分类、处理部门、建议编号及最终人工选择在同一创建事务中保存。负责人仍由用户单独指定，不自动从部门分派。
- “我的试点记录”统计本用户生成、人工确认保存、分类一致及部门一致次数。一致次数不表示模型准确率，未保存建议不计入人工确认数；记录不足不能推断效果。
- 无法判断、低置信度都不会自动执行；页面展示的置信度反映模型概率分布集中程度，不是正确率。
- 建议失败可继续手动建立异常，不使用伪造的规则结果冒充 Jev。

## 配置和部署

- 密钥按租户加密保存，页面只获知是否已配置；留空保留，明确清除才删除。启用必须已有密钥。
- 配置与连接测试需要现有 `mes:assistant:config` 权限；生成建议需要 `mes:insight:query` 与 `mes:insight:manage`。
- 新增迁移 `database/migrations/20261020_jev_incident_triage.sql`，只新增三张表，不重建或导入业务数据。
- 更新到已有部署时，先运行 `pwsh -File deploy/apply-migrations.ps1`，再使用 `pwsh -File deploy/restart-backend.ps1 -Build`。日常开机只需正常启动，不重复初始化。
- 传输继续验证公网DNS与HTTPS证书，不跟随重定向。如代理Fake-IP将 `api.typesafe.ai` 解析到 `198.18.x.x`，需要在代理DNS中为该域名配置排除，再重启后端；不要关闭项目地址保护。

在没有真实 TypeSafe 密钥时，可以完成代码、模拟响应、数据库与手动流程验证；这不等于已完成云端连通性或真实业务准确性验证。
